# 统一定价页（后台独立入口）

> 位置：后台 → 系统设置 → **统一定价**（侧栏第一组，`/system-settings/pricing/<section>`）
> 代码：`web/src/features/system-settings/pricing/`、`setting/pricing_policy.go`
> 状态：已完成并本地验证（保存链路实测通过）

---

## 1. 为什么单独做一页

New API 的价格参数原本散在四个地方：计费与支付（额度/货币/充值）、模型定价（倍率/按次）、
分组定价（分组倍率）、请求策略（预扣）。改一次价要在四个页面之间来回跳，且看不到任何
「改完值多少钱」的即时反馈。

这一页只解决两件事：

1. **把参数聚到一处**，并在每个参数旁边写清楚它的口径（单位、方向、坑）；
2. **给一个换算器**，让「上游成本 → 幕 → 实付 → 毛利」当场算出来。

它**不新建任何同义配置** —— 读写的都是原有 option 键，所以原页面照常可用，两边改的是同一份数据。

## 3. 三个设计要点

### 3.1 只提交真正变化的键

表单初始化时把整份 settings 作为 `original`，提交时逐键比对，只把差异项 `PUT /api/option/`。
JSON 类字段（`ModelRatio` 有 235 条）如果无脑整份回写，任何一次误触都会重排整张表。

### 3.2 保存前复核服务端值（防静默覆盖）

这一页与「模型定价」「计费与支付」共用同一批键。如果期间别人在原页面改了值，
这里直接提交会覆盖掉对方的修改且没有任何提示。

所以保存流程是：

```
1. 收集差异键
2. refetch 最新 option
3. 逐个比对：服务端现值 ≠ 进入页面时的值 → 中止 + 提示哪个键变了 + 自动刷新
4. 全部一致 → 依次提交
```

### 3.3 换算器不写配置

换算器只读 `pricing_policy.*` 与 `QuotaPerUnit`/`USDExchangeRate`，不落任何数据。
数字不对应该去改刻度，而不是改换算器 —— 页面底部写了这句话。

## 4. 换算公式（与 `docs/mu_billing_calc.py` 一致）

```
K          = QuotaPerUnit / QuotaPerMu          # 1 美元 = 多少幕
c_mu       = USDExchangeRate / K                # 单幕上游成本（元）
p_mu       = 1 / MuPerRMB                       # 单幕售价（元）
毛利       = 1 - c_mu / p_mu
raw 幕     = 成本(元) / c_mu
挂牌幕     = ceil 到 <1 取 0.1 / 1–20 取 0.5 / 20–100 取 1 / >100 取 2
建议 Price = QuotaPerUnit / (QuotaPerMu × MuPerRMB)
```

### 4.1 充值到账的真实口径（容易搞错）

```
payMoney = amount × Price           # Price = 1 美元额度卖多少元
quota    = amount × QuotaPerUnit    # 发额度按面额，与 Price 无关
```

所以「付 ¥100」= `amount = 100 / Price`，到账 `amount × QuotaPerUnit` quota。
页面把这条链路直接算给你看，而不是让你自己推。

## 5. 当前线上口径的一个已知偏差

按现有配置（`Price = 7.3`、`QuotaPerUnit = 500000`、`QuotaPerMu = 5136`、`MuPerRMB = 10`）：

| 项目 | 页面显示 |
|---|---|
| 计价刻度声明 | **10.00 幕 / ¥1** |
| 实际到账 | **13.34 幕 / ¥1**（充 ¥100 → 1333.6 幕） |
| 该笔充值上游成本 | ¥100.00 |
| 该笔充值毛利 | **0.00%** |
| 口径一致所需 Price | **9.735** |

原因：`Price = 7.3` 等于汇率本身，等于按成本价卖额度，毛利为 0。
要拿到 25% 的定价基准毛利，`Price` 应为 `7.3 / 0.75 = 9.733`，
恰好也等于 `QuotaPerUnit / (QuotaPerMu × MuPerRMB) = 9.735` —— 两个约束在 v3 常数下是同一个方程。

> **这是页面最重要的产出：它把「刻度说 10 幕/元、实际给 13.34 幕/元」这个静默偏差摆到了台面上。**
> 要不要改 `Price` 是经营决策（改了等于全线涨价 33%），页面只负责让决策者看见。

## 6. 与原有入口的关系

| 原有入口 | 状态 | 说明 |
|---|---|---|
| 计费与支付 → 额度设置 / 货币与展示 | ✅ 不变 | 与本页「充值与额度」「预扣与展示」读写同一批键 |
| 计费与支付 → 模型定价 | ✅ 不变 | 表格编辑器仍在，功能完整（289 个模型可正常加载） |
| 计费与支付 → 分组定价 | ✅ 不变 | 与本页「分组倍率」同源 |
| 计费与支付 → 支付网关 | ✅ 不变 | 本页不涉及支付渠道配置 |

两处并发编辑时的行为：**后保存的一方会被拦下**（§3.2 的复核），不会静默覆盖。

## 8. 上线前必须做

1. `cd web && bun run build` —— 前端是 `//go:embed web/dist`，不重新构建进不了二进制；
2. `go build -o new-api-local.exe .` —— `setting/pricing_policy.go` 需要注册进 OptionMap，不重启页面读不到 `pricing_policy.*`；
3. 部署后先看「计价刻度」的**实际毛利率**与「充值与额度」的**口径一致所需 Price**，再决定要不要动 `Price`。
